# Техническое задание на разработку сервис-деска с интеграцией Telegram

## 1. Задача для ИИ-разработчика

Разработать полноценное веб-приложение для обработки обращений клиентов, поступающих в Telegram-бота и подключённые Telegram-группы.

Сотрудники должны получать сообщения, отвечать клиентам из приложения, назначать ответственных, менять статусы и приоритеты, контролировать сроки и просматривать историю работы.

Результат — работающее приложение с интерфейсом, сервером, базой данных и реальной интеграцией Telegram. Демонстрационные данные допускаются только в отдельном режиме разработки.

Основной пользовательский сценарий:

1. Клиент пишет боту или в подключённую группу.
2. Сообщение поступает в приложение.
3. Система создаёт обращение либо добавляет сообщение в существующее.
4. Оператор находит обращение в очереди и берёт его в работу.
5. Оператор отвечает из приложения.
6. Клиент получает ответ в исходном Telegram-чате.
7. После решения оператор завершает обращение.
8. История переписки и действий сохраняется.

## 2. Границы проекта

В первую версию входят:

- Telegram-боты: личные сообщения и группы.
- Несколько подключённых ботов в одном рабочем пространстве.
- Клиенты, компании и история обращений.
- Статусы, приоритеты, ответственные и команды.
- Очереди, фильтры, поиск.
- Сообщения, вложения и внутренние заметки.
- Контроль сроков ответа и решения — SLA.
- Уведомления внутри приложения.
- Роли и права доступа.
- Базовые отчёты.
- Настройки и журнал действий.

В первую версию **не входят** Instagram, TikTok, WhatsApp, телефония, платежи, подписки, ИИ-автоответы и отдельные мобильные приложения. Не создавать для них неработающие кнопки или пустые разделы.

Интерфейс — на русском языке. Пользовательский текст должен корректно сохраняться и отображаться на русском, узбекском и английском, включая кириллицу и латиницу.

Все значения сроков, ограничений и оформления ниже являются начальными настройками проекта, если прямо не обозначены обязательным поведением.

## 3. Технологии и архитектура

Использовать модульный монолит: один серверный проект с разделением на функциональные модули.

| Компонент | Технология |
|---|---|
| Интерфейс | React + TypeScript |
| Сборка интерфейса | Vite |
| Маршрутизация | React Router |
| Получение и кеширование серверных данных | TanStack Query |
| Сервер | Python + Django |
| REST API | Django REST Framework |
| Обновления в реальном времени | Django Channels + WebSocket |
| База данных | PostgreSQL |
| Фоновые задачи | Celery |
| Очередь и временные данные | Redis |
| Вложения | Закрытое S3-совместимое хранилище |
| Развёртывание | Docker Compose |
| Внешний доступ | HTTPS через обратный прокси |

Подобрать совместимые поддерживаемые версии на момент реализации, зафиксировать зависимости и версии контейнеров. Не использовать плавающий тег `latest` в production-конфигурации.

PostgreSQL — основной источник данных. Потеря Redis не должна приводить к потере уже принятых сообщений и заданий отправки.

Взаимодействие с Telegram вынести в отдельный адаптер. Статусы, назначения, фильтры и SLA не должны зависеть от Telegram-команд.

## 5. Рабочие пространства и права доступа

Предусмотреть изоляцию организаций через сущность `Workspace`.

Для первого запуска создаётся одно рабочее пространство. Публичная регистрация компаний и биллинг не требуются.

Все обращения, подключения, клиенты, файлы и настройки принадлежат конкретному пространству. Проверять принадлежность на сервере, в фоновых задачах и WebSocket-подписках.

| Роль | Доступ |
|---|---|
| Администратор | Все данные своего пространства, сотрудники, подключения и настройки |
| Руководитель | Обращения и отчёты своих команд, назначения и передача |
| Оператор | Обращения доступных команд, взятие в работу и обработка назначенных ему обращений |
| Наблюдатель | Просмотр разрешённых данных без изменений |

Дополнительные правила:

- Оператор видит свободные обращения своих команд и может взять их.
- Публично отвечать и менять состояние обращения может ответственный, руководитель его команды или администратор.
- Другой оператор с доступом может оставить внутреннюю заметку.
- Руководитель и администратор могут переназначать обращения.
- Наблюдатель не отправляет сообщения, не оставляет заметки и не изменяет данные.
- Деактивация сотрудника отзывает его сессии. Его активные обращения должны быть переназначены либо возвращены в свободную очередь с записью в истории.
- Нельзя удалить или деактивировать последнего администратора пространства.

Авторизация браузера — через серверные сессии и защищённые cookies. Для изменяющих запросов использовать CSRF-защиту.

## 6. Основные модели данных

Внутренние идентификаторы — UUID. Номер обращения — отдельное последовательное число внутри рабочего пространства. Даты хранить в UTC, отображать в часовом поясе пространства; начальное значение — `Asia/Samarkand`.

Внешние Telegram ID хранить без потери точности, поддерживать отрицательные ID групп. В JSON передавать их строками.

| Модель | Основные поля |
|---|---|
| Workspace | Название, часовой пояс, настройки |
| User | Имя, логин, пароль, активность |
| Membership | Пользователь, пространство, роль |
| Team | Пространство, название |
| TeamMember | Команда, сотрудник |
| ChannelConnection | Пространство, тип, bot ID, username, зашифрованный токен, состояние |
| Company | Название, ИНН, примечание |
| Customer | Имя, компания, телефон при наличии, язык, дополнительные поля |
| CustomerIdentity | Клиент, платформа, внешний user ID |
| Conversation | Подключение, внешний chat ID, тип, название, режим обработки |
| ConversationParticipant | Чат, внешний участник, связь с клиентом при наличии |
| Ticket | Номер, чат, клиент при наличии, тема, статус, приоритет, команда, ответственный, версия |
| Message | Чат, автор, направление, видимость, текст, внешний ID, reply ID, thread ID, даты |
| TicketMessage | Сообщение, обращение, способ привязки |
| Attachment | Сообщение, имя, размер, MIME-тип, ключ объекта, состояние загрузки |
| InternalNote | Обращение, сотрудник, текст, вложения |
| TicketReadState | Обращение, сотрудник, последнее просмотренное сообщение |
| SLAPolicy | Приоритет, лимиты ответа и решения, расписание |
| SLAInstance | Обращение, тип срока, начало, дедлайн, паузы, результат |
| InboundEvent | Подключение, update ID, payload, состояние обработки |
| OutboundJob | Сообщение, состояние, число попыток, время следующей попытки, ошибка |
| AuditEvent | Сотрудник или система, действие, объект, изменения, время |
| Notification | Получатель, тип, объект, прочитано |
| SavedFilter | Владелец, название, условия |
| ReplyTemplate | Название, язык, текст |

Для полей обращения предусмотреть:

- `status`;
- `priority`;
- `assignee_id`;
- `team_id`;
- `created_at`;
- `updated_at`;
- `last_customer_message_at`;
- `last_agent_message_at`;
- `resolved_at`;
- `closed_at`;
- `version`.

**Обязательные ограничения базы:**

- Уникальность входящего события по подключению и `update_id`.
- Уникальность внешнего сообщения по подключению, чату и `message_id`.
- Уникальность номера обращения внутри пространства.
- Одно сообщение может иметь не более одной основной привязки к обращению.
- Назначенный сотрудник должен иметь доступ к команде обращения.
- Связанные объекты не могут принадлежать разным пространствам.

Создать индексы для очередей, ответственных, статусов, дедлайнов, внешних ID и истории сообщений.

## 7. Главное меню

Основное левое меню:

- Запросы.
- Клиенты.
- Отчёты.
- Настройки.
- Профиль сотрудника.

**При нажатии на «Запросы» непосредственно под этим пунктом раскрываются вложенные вкладки:**

| Вкладка | Условия |
|---|---|
| Активные | Статусы Новое, В работе, Ожидаем клиента, Ожидаем специалиста |
| Мои | Активные обращения, назначенные текущему сотруднику |
| Свободные | Активные обращения без ответственного |
| Просроченные | Активные обращения с нарушенным незавершённым сроком ответа или решения |
| Все запросы | Все доступные обращения, включая решённые и закрытые |

Требования:

- Повторное нажатие на «Запросы» сворачивает вложенные вкладки.
- Текущая вкладка подсвечивается.
- Рядом с каждой вкладкой отображается счётчик.
- Заголовок страницы соответствует выбранной вкладке.
- Состояние раскрытия сохраняется для сотрудника.
- Отдельную постоянную колонку «Стандартные фильтры» не создавать.
- Счётчики учитывают права сотрудника.
- Дополнительные фильтры страницы изменяют число результатов в заголовке, но не базовые счётчики бокового меню.

Неразобранные сообщения показывать отдельным индикатором в разделе запросов. Они не должны незаметно исчезать из рабочего процесса.

## 8. Список обращений

Основное представление — таблица.

| Колонка | Содержимое |
|---|---|
| Номер | Номер обращения |
| Клиент и тема | Клиент или группа, краткая тема |
| Последнее сообщение | Автор и начало текста |
| Статус | Текущее состояние |
| Приоритет | Название и цветовой индикатор |
| Ответственный | Сотрудник или «Не назначен» |
| Срок | Ближайший актуальный дедлайн |
| Непрочитанное | Количество непрочитанных сообщений |

Даты создания, обновления, команда и дополнительные данные — настраиваемые колонки.

Обязательное поведение:

- Нажатие на строку открывает обращение.
- Длинный текст сокращается визуально; полный доступен при наведении или открытии.
- Превью содержит автора: «Клиент», «Вы», имя сотрудника или «Бот».
- У свободного обращения доступна кнопка «Взять».
- Срок показывается понятным текстом: «Ответить за 04:32», «Просрочено на 12 мин», «На паузе».
- Цвет не является единственным способом передачи статуса.
- Пагинация выполняется сервером. Начальный размер страницы — 25 записей.
- Добавить сортировку по обновлению, приоритету, дате создания и ближайшему дедлайну.
- Обновления не сбрасывают фильтры, страницу и положение пользователя без необходимости.

Фильтры: статус, приоритет, ответственный, команда, подключение, клиент, компания, дата создания, непрочитанное.

Поиск: номер обращения, тема, клиент, название группы и текст доступной переписки. Поиск не должен раскрывать скрытые от сотрудника сообщения.

Состояние фильтров и сортировки сохранять в URL. Предусмотреть личные сохранённые фильтры.

## 9. Экран обращения

На широком экране использовать три области:

1. Список обращений текущей очереди.
2. Переписка выбранного обращения.
3. Карточка обращения и клиента.

Правая карточка содержит номер, тему, статус, приоритет, команду, ответственного, сроки, клиента, компанию и историю изменений.

В переписке отображать:

- Входящие и исходящие сообщения.
- Автора, дату и время.
- Фото, документы, видео и голосовые сообщения.
- Ответы на конкретные сообщения.
- Метку редактирования.
- Состояние отправки.
- Внутренние заметки.
- Системные события: назначение, передача, изменение статуса.

Поле ввода имеет два явно различимых режима: **«Ответ клиенту»** и **«Внутренняя заметка»**. При переключении сохранять отдельные черновики. Заметка не может быть отправлена в Telegram.

Предусмотреть шаблоны ответов, прикрепление файлов и понятное отображение ошибок. Использование шаблона только вставляет текст; отправку выполняет сотрудник.

Если клиент прислал новые сообщения, пока оператор читает старые, показывать кнопку перехода к ним, не перемещая прокрутку принудительно.

Общий чат и обращения в нём показывать раздельно. Просмотр других обращений того же чата требует проверки прав.

## 10. Статусы и переходы

| Код | Название | Значение |
|---|---|---|
| `new` | Новое | Обращение создано, работа не начата |
| `in_progress` | В работе | Обращение обрабатывается |
| `waiting_customer` | Ожидаем клиента | Нужны сведения от клиента |
| `waiting_specialist` | Ожидаем специалиста | Нужны действия другой команды |
| `resolved` | Решено | Решение предоставлено |
| `closed` | Закрыто | Обработка завершена |

Правила переходов:

- «Взять в работу» назначает сотрудника и переводит новое обращение в `in_progress`.
- Из `in_progress` доступны ожидание клиента, ожидание специалиста и решение.
- Из ожидания можно вернуться в работу.
- Поступление сообщения клиента в `waiting_customer` возвращает обращение в работу; если ответственного уже нет — в новое.
- Сообщение клиента при `waiting_specialist` создаёт потребность в ответе, но не отменяет ожидание специалиста.
- Из `resolved` доступно закрытие или повторное открытие.
- Переход в `closed` выполняется отдельным действием.
- Отправка ответа сама по себе не решает и не закрывает обращение.
- Для решения нужно заполнить краткий результат.
- Изменения фиксируются в журнале.

**Повторное обращение:**

Если сообщение однозначно связано с решённым обращением и поступило в пределах настраиваемого окна, обращение открывается повторно. Начальное окно — 24 часа после решения.

Если обращение закрыто, окно истекло или клиент выбрал «Новая проблема», создаётся новое обращение со ссылкой на предыдущее. Старые сообщения не переносятся автоматически.

Повторное открытие создаёт новый цикл SLA; показатели прошлого цикла сохраняются.

## 11. Приоритеты и назначения

| Код | Название |
|---|---|
| `low` | Низкий |
| `normal` | Обычный |
| `high` | Высокий |
| `critical` | Критический |

Начальный приоритет — обычный. Изменение приоритета записывается в историю.

При нажатии «Взять»:

- Сервер атомарно проверяет, что обращение свободно.
- Назначает сотрудника.
- Возвращает актуальную карточку.

При одновременном нажатии двумя сотрудниками только один получает обращение. Второму возвращается конфликт с информацией об актуальном ответственном.

При передаче в другую команду нужно одновременно выбрать нового допустимого ответственного либо явно оставить обращение свободным. Предыдущий ответственный не должен оставаться назначенным, если больше не имеет доступа.

## 12. Подключение Telegram

Экран подключения доступен администратору.

1. Администратор вводит токен бота.
2. Сервер проверяет токен и получает данные бота.
3. Создаёт подключение.
4. Настраивает webhook с отдельным секретом.
5. Показывает состояние подключения и инструкцию для групп.

Токен хранится зашифрованным, не возвращается интерфейсу после сохранения, не попадает в журналы, сообщения об ошибках и адреса, доступные пользователю. Может быть заменён администратором.

Состояния подключения: подключено, отключено вручную, ошибка авторизации, ошибка webhook.

Новый обнаруженный групповой чат должен быть подтверждён администратором перед полноценной обработкой. Добавление бота в произвольную группу не должно автоматически открывать её сообщения всем сотрудникам.

Для получения обычных сообщений групп нужно корректно настроить права бота или Privacy Mode. Приложение принимает только события, которые Telegram действительно передаёт: полную историческую переписку и сведения о прочтении обычных сообщений обещать нельзя.

Официальные источники: https://core.telegram.org/bots/faq и https://core.telegram.org/bots/api

## 13. Правила работы личных сообщений

- `/start` отправляет приветствие и кнопку «Создать обращение», но сам по себе не создаёт заявку.
- `/help` показывает справку.
- Текст или вложение при отсутствии открытых обращений создаёт новое.
- При одном открытом обращении сообщение добавляется в него.
- Клиент может явно выбрать «Новая проблема».
- При нескольких открытых обращениях бот предлагает выбрать нужное либо создать новое.
- До выбора входящие сообщения сохраняются в неразобранных, а не теряются.
- Кнопки выбора должны проверять пользователя, чат и доступность обращения.
- Повторное нажатие на кнопку не создаёт дубликат заявки.

Приветствие и технические сообщения бота обозначаются как автоматические и не учитываются как ответ оператора.

## 14. Правила работы групп

Предусмотреть два режима, выбираемых для каждой группы.

**Режим группы одного клиента.** Если есть одно активное обращение и нет более точной связи, сообщения добавляются в него. Если обращений несколько, неоднозначное сообщение попадает на разбор.

**Режим общей группы.** Обращение создаётся по команде `/new`, явному обращению к боту или вручную сотрудником. Обычная переписка без признаков обращения не создаёт заявки.

Приоритет определения связи:

1. Ответ на сообщение, уже связанное с обращением.
2. Тема Telegram, явно закреплённая за обращением.
3. Правило группы одного клиента.
4. Неразобранные сообщения — при обращении к поддержке без однозначной связи.

Нельзя связывать сообщения общей группы только по отправителю или времени: один человек может одновременно обсуждать разные проблемы.

Ответ оператора должен уходить в исходную группу, в исходную тему, если она есть, и ответом на выбранное сообщение, если оно доступно.

Если Telegram отклонил отправку из-за отсутствующего сообщения или темы, не менять получателя или тему молча. Показать причину и предложить допустимый вариант отправки.

Предусмотреть действие «Выделить в новое обращение». Оно меняет привязку выбранных сообщений с сохранением истории и проверкой прав.

## 15. Надёжность обработки сообщений

**Входящие события:**

- Проверять секрет webhook.
- Сохранять событие в PostgreSQL до подтверждения получения.
- При недоступной базе возвращать ошибку, а не успешное подтверждение.
- Повторное событие не создаёт повторное сообщение.
- Обработку выполнять фоново.
- Поддерживать повторную обработку после сбоя.
- Не полагаться на строгое поступление событий по порядку.
- Изменение сообщения обновляет существующую запись; более старая версия не перезаписывает новую.
- Неизвестный тип сообщения показывать как неподдерживаемый, а не отбрасывать без следа.

**Исходящие сообщения:**

Сообщение и задание отправки сохраняются в одной транзакции — использовать transactional outbox.

| Состояние | Значение |
|---|---|
| `queued` | Ожидает отправки |
| `sending` | Выполняется запрос |
| `sent` | Telegram подтвердил успех |
| `failed` | Получена определённая ошибка |
| `unknown` | Запрос мог выполниться, но подтверждение не получено |

Правила:

- Повторное нажатие «Отправить» с тем же ключом операции не создаёт новую отправку.
- Обрабатывать ограничения частоты и `retry_after`.
- Автоматически повторять только безопасные попытки.
- При неизвестном результате не выполнять слепой повтор.
- Ручной повтор неизвестной отправки должен предупреждать о возможном дубликате.
- После сбоя работника зависшая отправка проверяется; её нельзя безусловно считать неотправленной.
- Ошибки блокировки бота или утраты прав показываются сотруднику.
- После восстановления Redis незавершённые задания обнаруживаются по базе.

## 16. Вложения

Обязательная поддержка:

- Приём текста, фотографий, документов, видео и голосовых сообщений.
- Просмотр фотографий.
- Проигрывание поддерживаемых браузером аудио и видео.
- Скачивание доступных документов.
- Отправка текста, фотографий и документов.

Для остальных типов показывать понятное обозначение без потери самого факта сообщения.

Требования:

- Проверять размер и фактический тип файла.
- Не доверять расширению имени.
- Хранить файлы в закрытом хранилище.
- Проверять доступ при скачивании.
- Не передавать клиентскому браузеру Telegram URL с токеном бота.
- Скачивание выполнять фоново.

- Не исполнять и не отображать активное HTML-содержимое вложений как часть интерфейса.

## 17. SLA и рабочее время

Реализовать три независимых показателя: первый ответ сотрудника, следующий ответ на новое сообщение клиента, решение обращения.

Начальные значения для запуска:

| Приоритет | Первый ответ | Следующий ответ | Решение |
|---|---|---|---|
| Низкий | 60 минут | 120 минут | 24 рабочих часа |
| Обычный | 15 минут | 30 минут | 8 рабочих часов |
| Высокий | 5 минут | 10 минут | 4 рабочих часа |
| Критический | 2 минуты | 5 минут | 1 рабочий час |

Значения редактируются администратором. Начальное расписание — круглосуточное; дополнительно поддержать дни недели, интервалы работы и исключения.

Правила расчёта:

- Отсчёт начинается с сохранения соответствующего входящего сообщения.
- Несколько сообщений подряд не переносят уже установленный срок ответа.
- Автоответ, внутренняя заметка и назначение сотрудника не останавливают срок ответа.
- Срок ответа завершается после подтверждённой отправки публичного ответа сотрудника.
- Сообщения клиента, поступившие после начала этой отправки, не должны ошибочно считаться обработанными.
- Ожидание клиента приостанавливает только срок решения.
- Ожидание специалиста по умолчанию не приостанавливает сроки.
- Передача между сотрудниками не обнуляет время.
- При изменении приоритета пересчитывать бюджет с учётом уже потраченного времени.
- Зафиксированные нарушения не удалять из истории.
- Просроченность определяется сервером; таймер в браузере только отображает её.
- Длительная недоступность приложения не обнуляет сроки.

Изменение SLA-политики применяется к новым циклам. Пересчёт действующих обращений — отдельная явная операция администратора с журналированием.

## 19. Обновления в реальном времени

WebSocket передаёт события:

- Обращение создано или изменено.
- Получено новое сообщение.
- Изменилось состояние отправки.
- Изменился ответственный.
- Создано уведомление.
- Нужно обновить счётчики.

Каждое событие имеет ID, тип, время, ID объекта и версию.

WebSocket не является единственным источником истории. После переподключения интерфейс запрашивает актуальные данные через API.

Повторные события не создают дубли. После отзыва доступа подписка прекращается.

## 20. Уведомления и отчёты

Уведомления внутри приложения:

- Назначено обращение.
- Клиент написал в назначенном обращении.
- Приближается срок.
- Срок нарушен.
- Ответ не отправлен.
- Подключение Telegram требует внимания.

Всплывающие уведомления не перекрывают основные кнопки и таблицу. Одинаковые частые события объединяются.

Базовые отчёты:

- Созданные, решённые и закрытые обращения за период.
- Активные и свободные обращения на текущий момент.
- Медиана и 90-й процентиль времени первого ответа.
- Время решения.
- Доля выполненных SLA.
- Повторно открытые обращения.
- Нагрузка по сотрудникам и командам.

В отчётах явно указать, по какой дате отбираются данные и в каких единицах рассчитано время. Автоматические ответы не учитывать как ответы сотрудников. Обращения без ответа показывать отдельно, не считать их время равным нулю.

## 21. Интерфейс и адаптивность

Визуальный стиль — спокойный рабочий интерфейс с высокой читаемостью и умеренной плотностью.

Требования:

- Светлая и тёмная темы.
- Чёткая иерархия текста.
- Никаких декоративных блоков, мешающих работе с обращениями.
- Статусы, ошибки и приоритеты обозначаются текстом и цветом.
- Кнопки доступны с клавиатуры, фокус заметен.

- На небольшом экране меню скрывается, переписка занимает основную область, свойства открываются отдельной панелью.
- На телефоне все основные действия доступны без обязательной горизонтальной прокрутки.

Названия, логотипы и реальные клиентские данные из предоставленного примера не копировать. Начальное название приложения — **Service Desk**.

## 23. Производительность

Критерии на зафиксированном тестовом сервере:

- Список обращений не создаёт отдельный SQL-запрос для каждой строки.

Дополнительно должны пройти проверки групп, повторных событий, конкурирующих назначений, SLA, прав доступа и восстановления после сбоя.
