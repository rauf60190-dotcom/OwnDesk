# Регистрация пользователей

## Локальная проверка

`Start-Portal.ps1` запускает отдельный портал на `127.0.0.1:5175` и включает регистрацию с тестовым письмом. Сервер организации на 5173 принимает сотрудников только по приглашениям. Выйдите из существующего аккаунта и выберите «Зарегистрироваться по email». Введите имя и адрес. Ссылка подтверждения появится в блоке «Тестовое письмо». После перехода задайте пароль не короче 12 символов.

Настоящее письмо в Gmail или другую почту в этом режиме не отправляется. На портале создаётся только аккаунт. Организация, команда и политики SLA создаются отдельно в мастере настройки сервера организации. Существующие клиенты, Telegram-боты и переписка не копируются.

Локальный аккаунт не считается подтверждённым почтовым аккаунтом (`email_verified=false`, `is_local_account=true`). Его вход и сессия действуют только при DEBUG и LOCAL_EMAIL_PREVIEW. Тестовая ссылка не работает из внешней сети. Повторная регистрация с тем же адресом не заменяет существующий аккаунт: используйте вход с паролем.

## Настоящая регистрация по email

На сервере задайте PUBLIC_REGISTRATION_ENABLED=1, LOCAL_EMAIL_PREVIEW=0, PUBLIC_BASE_URL с HTTPS-адресом и SMTP-параметры из .env.example. DEBUG должен быть выключен. Для порта 587 обычно используется EMAIL_USE_TLS=1, EMAIL_USE_SSL=0; для 465 — EMAIL_USE_TLS=0, EMAIL_USE_SSL=1. Выберите параметры своего почтового провайдера. Пароль SMTP храните в .env вне архива и репозитория.

Письма отправляются фоновой задачей Celery. Запуск портала на ноутбуке использует отдельный процесс отправки. Ссылка одноразовая и действует 30 минут. Пароль устанавливается после перехода по ссылке. В базе сохраняется хеш токена, а тело письма очищается после отправки, ошибки с неизвестным результатом или истечения срока. При неизвестном результате SMTP пользователь может запросить новую ссылку.

Запросы ограничены по email и сетевому источнику. По умолчанию лимит использует адрес соединения с приложением. Для прокси на том же компьютере можно включить `TRUST_LOOPBACK_CLIENT_IP=1`. При этом прокси должен заменять `X-OwnDesk-Client-IP` проверенным адресом посетителя. Для входящих запросов через Cloudflare Tunnel таким источником служит `CF-Connecting-IP` при закрытом прямом доступе к прокси и приложению. [Заголовки Cloudflare](https://developers.cloudflare.com/fundamentals/reference/http-headers/).

## Google

### Текущее состояние owndesk.work

На 18 ноября 2026 реквизиты Google OAuth и SMTP Resend сохранены в закрытой конфигурации работающего портала. Публичный API возвращает `google_login=true`, `email_registration=true`, `local_email_preview=false`. Проверены настоящее письмо регистрации в Gmail владельца, создание отдельного тестового аккаунта по одноразовой ссылке, отказ повторной ссылки и вход с паролем. Основной аккаунт не менялся; тестовый аккаунт оставлен по явному решению владельца. Google с отдельным аккаунтом остаётся внешней приёмкой. Подробности: [состояние подключения и внешняя приёмка](PUBLIC-REGISTRATION-LAUNCH.md).

Не следует считать статус Google Testing безусловным запретом для всех, кроме тестовых пользователей. OwnDesk запрашивает только `openid email profile`: для этих базовых scopes Google описывает исключение из требования списка тестовых пользователей и семидневного срока авторизации. Доступ конкретного аккаунта всё равно могут ограничивать политики Google Workspace. Оформление бренда и проверка домена — отдельные задачи. См. [правила аудитории Google](https://support.google.com/cloud/answer/15549945?hl=en).

Создайте OAuth-клиент типа Web application в Google Cloud, настройте экран согласия и укажите точный redirect URI:

```
https://your-domain/api/v1/auth/google/callback
```

Для проверки на компьютере можно зарегистрировать `http://127.0.0.1:5173/api/v1/auth/google/callback` и задать такой же PUBLIC_BASE_URL. Сохраните GOOGLE_CLIENT_ID и GOOGLE_CLIENT_SECRET в окружении процесса. Приложение запрашивает только openid, email и profile. Клиентский секрет браузеру не передаётся. До настройки ключей вход через Google недоступен. Используйте обычный браузер, если Google запрещает авторизацию во встроенном браузере.

Проверяются подпись RS256, issuer, audience, срок действия, nonce, state, PKCE и подтверждение email. Идентификатор аккаунта Google — sub. Совпадение email не объединяет автоматически Google-аккаунт с существующим аккаунтом сотрудника. Если адрес уже зарегистрирован с паролем, используется вход с паролем. Секреты и токены Google не сохраняются в профиле.

Документация: [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect), [проверка JWT](https://pyjwt.readthedocs.io/en/2.15.1/usage.html).

## Проверено и ограничения

Проверены серверные сценарии подтверждения, срока ссылки, повторного использования, ограничений запросов, CSRF, изоляции пространств, повторного входа Google и отказа при неверных claims. Google в автоматических тестах использует локальные подписанные токены и подменённый ответ обмена кода. Реквизиты настоящего Google OAuth настроены; текущая read-only проверка не доказывает внешнюю приёмку с отдельным аккаунтом. Настоящий SMTP подключён. Кроме тестового транспорта Django, пройден публичный сценарий настоящего письма, подтверждения и входа с паролем на отдельном тестовом профиле. Интерактивный выбор пароля посетителем в браузере в этой внешней проверке не проверялся: HTTP-сценарий использовал случайный тестовый пароль; локальная браузерная проверка формы описана ниже.

В браузере на отдельной файловой тестовой базе пройден полный локальный сценарий регистрации, вход по email, отказ при повторном подтверждении и экран 390 px. Работающие клиентские чаты не использовались.

Портал опубликован по адресу `owndesk.work`. Следующие проверки — Google OAuth с отдельным аккаунтом и интерактивный сценарий нового пользователя в браузере. Подготовленную страницу конфиденциальности ещё нужно безопасно опубликовать.
