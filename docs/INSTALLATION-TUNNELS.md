# Отдельный адрес организации

Выпуск 0.4.17 добавляет коннектор, который получает отдельный токен туннеля, управляет процессом `cloudflared` и подтверждает готовность сервера через публичный HTTPS-адрес. Общий ключ управления Cloudflare остаётся на портале. Подготовка ресурсов выполняется администратором портала. Обычный `Setup-OwnDesk.cmd` пока запускает локальный режим: он не включает публичный доступ.

## Подготовка портала

Домен должен обслуживаться Cloudflare. В закрытом окружении процесса портала задаются:

- `CLOUDFLARE_API_TOKEN`: токен с Cloudflare Tunnel Edit для нужного аккаунта и DNS Edit для зоны OwnDesk.
- `CLOUDFLARE_ACCOUNT_ID`: идентификатор аккаунта.
- `CLOUDFLARE_ZONE_ID`: идентификатор зоны.
- `INSTALLATIONS_DOMAIN`: по умолчанию `owndesk.work`.

Реквизиты нельзя добавлять в архив, клиентскую сборку или отправлять в чат. Созданный ранее токен запуска одного туннеля не заменяет токен управления API.

После применения миграций владелец создаёт код в «Мои установки», затем вводит его в мастере сервера организации. Начиная с 0.4.19 коннектор подготавливает маршрут автоматически при запросе конфигурации; в мастере также доступна кнопка «Подготовить адрес организации». Для диагностики администратор портала может выполнить из папки `backend`:

```text
python manage.py prepare_public_route UUID_УСТАНОВКИ
```

Команда создаёт отдельный туннель с именем `owndesk-UUID`, затем проксируемую CNAME-запись `org-UUID_БЕЗ_ДЕФИСОВ.owndesk.work`. Такой адрес не зависит от названия компании и не конфликтует с основным порталом. Выбор красивого адреса можно добавить позднее.

При потере ответа повторите ту же команду. Поиск по постоянному имени позволяет восстановить созданный туннель, а DNS проверяется до создания. Чужая запись не перезаписывается. Состояние `error` означает, что подготовку нужно повторить; `prepared` означает, что ресурсы созданы.

## Что работает и что ещё требуется

Подготовленный маршрут отвечает `404`. При первом запросе конфигурации коннектор получает токен только своего туннеля; маршрут разрешает только `/api/v1/connector/proof`. Коннектор проверяет локальный сервер, запускает туннель и просит портал проверить публичный HTTPS-адрес. Портал проверяет подпись одноразового запроса, привязанную к установке, hostname и готовности рабочего режима. Перенаправления при проверке не разрешены. Только после правильного ответа разрешается полный интерфейс.

В кабинете ссылка появляется только при подтверждении адреса и связи за последние 90 секунд. Коннектор повторяет проверку каждые 30 секунд, перезапускает завершившийся процесс, останавливает его при сетевой ошибке и пытается подключиться снова. Ответ портала об отзыве останавливает коннектор. Токен передаётся `cloudflared` через окружение, не через аргументы процесса, и не записывается в журнал или файл состояния.

## Запуск коннектора рабочего сервера

Это инструкция для администратора уже настроенной рабочей установки. Распределённая конфигурация использует PostgreSQL, Redis, worker и закрытое хранилище из [инструкции Linux](LINUX-DEPLOYMENT.md). Для одной организации доступен [нативный режим](NATIVE-RUNTIME.md) без Redis и Docker. Универсальный перенос базы локального мастера SQLite пока не встроен в установщик.

1. Обновите портал и сервер организации до одной версии, примените миграции. Привяжите установку и подготовьте её адрес командой выше.
2. В закрытом окружении сервера и коннектора задайте `DEPLOYMENT_MODE=organization`, `DEBUG=0`, постоянный случайный `SECRET_KEY` длиной не менее 50 символов, `DATABASE_URL` PostgreSQL и остальные рабочие реквизиты. Существующий рабочий секрет не заменяйте при каждом запуске.
3. Укажите `PUBLIC_BASE_URL=https://org-UUID_БЕЗ_ДЕФИСОВ.owndesk.work`, точный hostname в `ALLOWED_HOSTS` без `*` и этот HTTPS-origin в `CSRF_TRUSTED_ORIGINS`. Значения secure-cookie и HTTPS-перенаправления при `DEBUG=0` включены настройками OwnDesk. Приглашения используют `PUBLIC_BASE_URL`.
4. Задайте абсолютный `PORTAL_CONNECTOR_STATE_FILE`, указывающий на закрытый файл привязки с `id` и `connector_key`. Один и тот же файл должен быть доступен серверу и коннектору. Не раздавайте его сотрудникам: ключ разрешает получение токена запуска выделенного туннеля.
5. Запустите ASGI-сервер на loopback `127.0.0.1:8000`, например `daphne -b 127.0.0.1 -p 8000 config.asgi:application` из `backend`. Запустите настроенные worker и beat.
6. Для входа туннеля на этом же компьютере используйте [Caddyfile.connector](../infra/Caddyfile.connector). В окружении Caddy задайте `OWNDESK_DIST_DIR` — абсолютный путь к `frontend/dist`, затем выполните `caddy run --config infra/Caddyfile.connector --adapter caddyfile` из корня проекта. Конфигурация слушает только `127.0.0.1:5173`, обслуживает сборку интерфейса и передаёт API/WebSocket серверу на 8000. Порты не нужно открывать в роутере. Локальный сервер из `Setup-OwnDesk.cmd` на 5173 должен быть остановлен до запуска этой конфигурации.
7. Установите официальный `cloudflared`. Из `backend` в том же закрытом рабочем окружении выполните:

```text
python manage.py run_connector --state АБСОЛЮТНЫЙ_ПУТЬ_К_ФАЙЛУ_ПРИВЯЗКИ --cloudflared ПУТЬ_К_CLOUDFLARED
```

Команда контролирует только свой дочерний процесс. Ctrl+C или SIGTERM останавливает этот процесс; системные туннели других приложений не затрагиваются. Второй экземпляр коннектора для того же файла привязки не запускается.

Безопасный диагностический файл находится рядом с привязкой, с суффиксом `.status.json`: `checking`, `active`, `error`, `revoked` или `stopped`. В нём нет токенов. `checking` на первом подключении может означать ожидание DNS, сертификата или подключения туннеля. `error` требует проверки рабочего окружения, локального прокси, доступности портала и сети.

Автоматическая подготовка PostgreSQL/Redis/хранилища на Windows, миграция локальных данных, загрузка проверенной версии `cloudflared`, общий запуск процессов и установка фоновой службы ещё не реализованы. До этого этапа сотрудникам нельзя отправлять адрес локального мастера вместо готового публичного адреса.

## Отзыв доступа

Кнопка отзыва привязки сначала заменяет конфигурацию туннеля на `404`, затем удаляет DNS-запись. Только после успешного ответа Cloudflare портал подтверждает отзыв привязки. При ошибке показывает сообщение и позволяет повторить операцию. Туннель сохраняется закрытым для диагностики; его автоматическое удаление пока не реализовано.

Изменения конфигурации и DNS применяются Cloudflare не мгновенно. Этот этап не заявляет немедленное завершение уже открытых соединений. Для публичной приёмки нужно отдельно проверить время отключения активного браузерного соединения и доступ по старой ссылке.

Реализация использует [официальный API Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel-api/) и [параметры запуска cloudflared](https://developers.cloudflare.com/tunnel/reference/run-parameters/).
