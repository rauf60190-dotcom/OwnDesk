# Запуск регистрации OwnDesk

## Состояние на 18 ноября 2026

Рабочий портал доступен на `https://owndesk.work`. Google-клиент подключён, сервер разрешает создание аккаунта портала через Google. SMTP Resend подключён, публичный API возвращает `email_registration=true`, `google_login=true`, `local_email_preview=false`. Почтовый обработчик включён.

В аккаунте владельца Resend создан и подтверждён домен `auth.owndesk.work` (регион Tokyo, `Verified / Ready`). В Cloudflare добавлены точные записи из его панели: TXT `resend._domainkey.auth` и CNAME `rsend.auth`, `send.auth` с отключённым проксированием. Предварительная проверка не обнаружила конфликтов, все пять MX корневого домена сохранены. Точное совпадение трёх записей отдельно проверено через публичный DNS 1.1.1.1. В Resend включён `Enforced TLS`: при отсутствии TLS у принимающего сервера письмо не отправляется незашифрованным. Отслеживание открытий и переходов не подключено.

С отдельного подтверждения владельца создан ключ `OwnDesk registration SMTP` с `Sending access` только для `auth.owndesk.work`. Первый неиспользованный ключ попал в технический вывод при закрытии диалога; с отдельного подтверждения владельца он удалён. Замещающий ключ перенесён из каталога с ограниченным ACL в закрытую конфигурацию портала без вывода секрета; временные файлы обоих ключей удалены после применения. Публичные DNS-план и протокол: `work/resend-dns-plan.json`, `work/resend-dns-applied.json`, `work/resend-public-dns-proof.json`.

Подключение проверено с настоящим SMTP: успешная аутентификация, STARTTLS с TLSv1.3 и согласованное тестовое письмо владельцу. Gmail подтвердил получение во «Входящих» в 09:49:55 Asia/Tashkent 18 ноября 2026. Это тест транспорта SMTP, а не полный сценарий новой регистрации. Google-реквизиты сохранены; закрытая резервная копия прежних настроек находится в `MailConfigurationBackups` внутри каталога данных портала. Перезапущена только `OwnDeskPortal`, `OwnDeskServer` не перезапускалась. Публичный health отвечает `ok`, оба метода регистрации доступны. Протоколы: `work/resend-smtp-connected.json`, `work/resend-smtp-service-result.json`, `work/resend-delivery-proof.json`. Создание нового аккаунта по реальной ссылке, выбор пароля и вход с другим Google-аккаунтом остаются внешней приёмкой.

Портал Windows обновлён до 0.4.37: опубликованы новая страница конфиденциальности, кабинет владельца и витрина для гостя на корневом адресе. Вход — `/login`, кабинет — `/cabinet`, явная витрина — `/welcome`. Сервер организации остаётся на 0.4.26, общий опубликованный установочный дистрибутив — 0.4.35. Для самого подключения SMTP новая версия приложения не требовалась: это защищённая конфигурация. Реквизиты Google/SMTP и данные сохранены при обновлении интерфейса.

## Как это будет выглядеть для пользователя

1. Посетитель открывает OwnDesk и выбирает Google либо регистрацию по email.
2. При Google-входе подтверждает аккаунт на странице Google. OwnDesk получает идентификатор аккаунта, подтверждённый email и имя, без доступа к почтовому ящику.
3. При регистрации по email получает одноразовую ссылку на 30 минут, переходит по ней и задаёт собственный пароль от 12 символов. Готовый пароль письмом не отправляется.
4. В кабинете подключает собственную установку организации. Чаты, тикеты и вложения организации остаются на её сервере.
5. Сотрудников приглашают в организацию отдельной ссылкой. Они входят по HTTPS-адресу организации, доступ определяется назначенной ролью.

## Почтовый сервис: выбран Resend

Почтовый сервис доставляет письма от приложения в Gmail и другие ящики. Владельцу OwnDesk нужен один аккаунт сервиса; посетителям отдельный аккаунт Resend не требуется.

Для начала: открыть [регистрацию Resend](https://resend.com/signup) и самостоятельно войти или создать бесплатный аккаунт. Не отправлять пароли и API-ключи в чат. Проверять текущие лимиты и условия на [странице тарифов](https://resend.com/pricing); подключение платного тарифа в этот этап не входит.

### Домен и отправитель

Планируемый почтовый поддомен — `auth.owndesk.work`, отправитель — `OwnDesk <accounts@auth.owndesk.work>`. Это исходящий адрес; отвечать на него нельзя обещать, пока не настроен приём писем. Рабочий контакт поддержки нужно согласовать отдельно.

1. В Resend добавить `auth.owndesk.work` как домен отправки.
2. Получить точные DNS-записи из панели Resend и добавить их в Cloudflare. Не копировать примерные DKIM/SPF-значения из инструкции. Сверить, что имена относятся к выбранному поддомену и не конфликтуют с существующими записями. В текущем Resend Forge панель выдала CNAME для отправки, а не привычный набор TXT SPF + MX; использовать фактически выданные записи.
3. Существующие MX корневого `owndesk.work` для Namecheap forwarding сохранить. Если Resend выдаст MX для своего bounce-поддомена, применять только выданное имя внутри `auth.owndesk.work`.
4. Дождаться подтверждения домена. Создать ключ только для отправки и ограничить выбранным доменом, если интерфейс провайдера позволяет. Сохранить секрет только в закрытой конфигурации портала.
5. Отключить отслеживание открытий и переходов для писем входа; ссылки подтверждения не должны становиться ссылками рекламного трекинга.

Выделенный поддомен для почты рекомендован в [документации Resend](https://resend.com/docs/dashboard/domains/introduction). Никакой второй домен покупать не нужно.

### Настройки портала

В защищённом `C:\ProgramData\OwnDesk\Portal\integrations.json` сохранить существующие Google-поля и добавить:

| Параметр | Значение |
|---|---|
| `EMAIL_HOST` | `smtp.resend.com` |
| `EMAIL_PORT` | `587` |
| `EMAIL_HOST_USER` | `resend` |
| `EMAIL_HOST_PASSWORD` | секретный ключ Resend, без публикации в инструкции |
| `EMAIL_USE_TLS` | `1` |
| `EMAIL_USE_SSL` | `0` |
| `DEFAULT_FROM_EMAIL` | `OwnDesk <accounts@auth.owndesk.work>` |
| `PUBLIC_REGISTRATION_ENABLED` | `1` |

Все значения в JSON — строки. `mail_enabled` в `runtime-profile.json` должен быть boolean `true` (уже включён). Удалять или пересоздавать Google-клиент, базу и аккаунты не требуется. Параметры подтверждены [официальной инструкцией SMTP](https://resend.com/docs/send-with-smtp).

## Проверка конфигурации без раскрытия секретов

Из каталога исходников или будущей сборки с этим инструментом:

```powershell
python infra/public_auth_check.py --data-dir C:\ProgramData\OwnDesk\Portal
```

Для защищённого каталога нужны соответствующие права чтения. Команда только читает два JSON-файла, не обращается к базе и сети, не выводит значения ключей, email или SMTP-паролей. Код выхода `0` — конфигурация обоих способов заполнена; `2` — есть недостающие или неподходящие настройки; `1` — файл недоступен или некорректен. Отсутствующие SMTP-реквизиты считаются неготовностью. Этот инструмент ещё не входит в опубликованный архив 0.4.35.

Даже успешный результат — только предварительная проверка. Он не доказывает DNS-верификацию, успешный вход в SMTP, доставку письма, состояние Google Cloud или работоспособность фонового процесса после старта. В отчёте `external_acceptance_performed` всегда `false`.

Проверено 18 ноября 2026: 25 автоматических проверок инструмента прошли, включая сокрытие значений секретов и отказ при неверных файлах/настройках. До подключения SMTP read-only запуск с доступом к реальному защищённому каталогу портала вернул ожидаемый код `2`: Google настроен, SMTP host/credentials/sender отсутствовали, mail worker включён. После подключения SMTP выполнена повторная проверка. Её актуальный протокол в рабочем каталоге: `work/public-auth-check-result.json` и `work/public-auth-check-status.json`. Эти проверки не изменяют конфигурацию и базы.

## Внешняя приёмка

- Согласовать адрес получателя теста. Через обычный публичный экран зарегистрировать новый тестовый адрес; дождаться письма в реальном ящике и проверить папку «Спам».
- Убедиться, что письмо содержит HTTPS-ссылку собственного домена и не содержит пароль. Открыть ссылку, задать пароль, войти и выйти. Повторное использование ссылки должно отклоняться.
- Проверить восстановление доступа тем же способом. Секреты, ссылки и содержимое писем не записывать в публичный протокол.
- Проверить Google-вход с отдельным аккаунтом. Запрос scopes должен оставаться `openid email profile`; не добавлять Gmail API или доступ к Drive ради регистрации.
- Проверить, что аккаунт портала не получает доступ к данным чужих организаций и не превращается автоматически в сотрудника организации.
- Зафиксировать результат доставки отдельно от проверки настроек. При неудаче вернуть прежнюю конфигурацию; базы и пароли пользователей не откатывать.

## До широкого запуска

Полный настоящий сценарий регистрации проверен 18 ноября 2026 на отдельном тестовом аккаунте Gmail владельца: письмо во «Входящих», подтверждение адреса, вход с паролем и отказ повторного использования ссылки. Протоколы: `work/registration-mail-acceptance-result.json`, `work/registration-mail-receipt-proof.json`; результат удаления только созданного тестового профиля — `work/registration-mail-cleanup-result.json`. Основной аккаунт не изменялся.

Владелец согласовал свой Gmail как публичный контакт по вопросам данных. На `https://owndesk.work/privacy` опубликована и проверена [страница конфиденциальности](PRIVACY-PAGE.md) с отдельными разделами о портале, организациях, Google, Resend, Cloudflare, Telegram и запросах на удаление. Сведения об операторе и конкретные сроки хранения не следует выдумывать; эти вопросы остаются до широкого запуска.

В Google Branding сохранены ссылки на витрину и политику. Следующие отдельные проверки — вход с другим Google-аккаунтом и, при необходимости, верификация бренда/владения доменом. Базовые scopes имеют исключение для Testing; сохранение URL не меняет статус Testing и не является верификацией бренда. См. [Google Audience](https://support.google.com/cloud/answer/15549945?hl=en) и [требования к приложениям аутентификации](https://developers.google.com/identity/verification/authentication-policy-compliance).
