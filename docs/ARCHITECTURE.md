# Архитектура и принятые решения

Проект состоит из модулей одного Django-приложения. React запрашивает `/api/v1/` через TanStack Query и хранит навигацию в React Router. PostgreSQL хранит рабочие данные, входящие события и задания отправки. Redis используется для Celery и событий Channels. Файлы размещаются в закрытом S3-совместимом бакете.

| Решение | Практическое следствие |
|---|---|
| UUID для внутренних объектов, отдельный счётчик номера в пространстве | Блокировка строки пространства защищает номер обращения от одновременной выдачи |
| Область доступа формируется на сервере | Администратор видит своё пространство, остальные сотрудники — доступные команды. Выборка очереди, журнал, файлы, чат и WebSocket проверяют права |
| Строка обращения блокируется перед изменением | `expected_version` обнаруживает устаревшую карточку. Повторный захват свободного обращения получает HTTP 409 |
| Одно поле `Message.ticket` задаёт основную привязку | Сообщение принадлежит максимум одному обращению. Перенос фиксируется в истории. Внутренняя заметка имеет `visibility=internal` и никогда не создаёт OutboundJob |
| Ограничения и триггеры PostgreSQL | Защищают область пространства, привязку сообщения к чату и допустимость ответственного при записи обращения |
| Два этапа обработки webhook | HTTP-запрос проверяет секрет и сохраняет событие. Worker разбирает его позже. Уникальны пары «подключение + update_id» и «чат + message_id» |
| Сообщение и OutboundJob создаются в одной транзакции | Потеря очереди брокера позволяет восстановить работу из PostgreSQL. Beat регулярно обнаруживает сохранённые задания |
| Отправка учитывает неопределённый результат | Worker фиксирует `sending` перед внешним запросом. Потерянное подтверждение или остановка работника приводит к `unknown`. Ограничения частоты используют `retry_after` |
| Версия обращения отделяет сообщения до отправки и после неё | Worker запоминает версию перед запросом в Telegram. Подтверждение завершает только срок ответа на уже известные сообщения, в том числе при одинаковых отметках времени |
| SLA отсчитывается от сохранения webhook | Задержка фоновой обработки не сбрасывает сроки. Новые сообщения сохраняют действующий срок ответа. Закрытие заявки без ответа отменяет цикл ответа и не добавляет фиктивный результат в отчёт |
| Политики и расход времени сохраняются у каждого цикла | Изменения правил применяются к новым циклам. Администратор может отдельно пересчитать действующие сроки. Паузы и уже потраченное рабочее время учитываются при изменении бюджета |
| WebSocket передаёт сигнал обновления | Тело сообщения и история загружаются через API с повторной проверкой прав. При переподключении интерфейс обновляет данные |
| Отдельный режим локального просмотра | Демонстрационные данные и SQLite доступны в режиме разработки. Рабочая конфигурация Compose использует PostgreSQL и HTTPS |

Вложения ограничены 20 МиБ. Сервер определяет распознаваемые типы по сигнатуре, выдаёт скачивание после проверки прав и не передаёт браузеру Telegram URL. Сроки хранения настраиваются администратором. По умолчанию удаление по возрасту отключено. После очистки технического payload остаётся идентификатор события для защиты от повторов.

Версии Python-пакетов зафиксированы в `backend/requirements.txt`, версии фронтенда — в `frontend/pnpm-lock.yaml`, образы — в Compose и Dockerfile. Для сервера выбрана поддерживаемая ветка Django 5.2 LTS. [Поддерживаемые версии Django](https://www.djangoproject.com/download/)
