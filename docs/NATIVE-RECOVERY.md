# Восстановление копии в отдельный стенд Windows

Вкладка «Восстановление данных» в `Setup-OwnDesk-Server.cmd` восстанавливает копию служб OwnDesk с PostgreSQL в новый закрытый каталог. Рабочая установка не перезаписывается и не останавливается. После проверки восстановленная база остаётся остановленной; приложение и внешние интеграции не запускаются.

Это подготовка и проверка восстановления, а не автоматическое переключение рабочего сайта на старые данные. Такой переход требует отдельного сравнения данных, проверки приложения и решения владельца о моменте восстановления.

## Порядок действий

1. Распакуйте дистрибутив и откройте `Setup-OwnDesk-Server.cmd`. Подтвердите стандартный запрос администратора Windows.
2. На вкладке «Восстановление данных» выберите каталог завершённой копии с `manifest.json`, созданной [инструментом копирования служб](NATIVE-BACKUPS.md).
3. Нажмите «Проверить копию». Проверяются файлы, SHA-256, ключи, версия и перечень таблиц. Изменение каталога сбрасывает результат проверки.
4. Нажмите «Восстановить отдельно». Если копия изменилась после проверки, операция откажется её использовать. Каталог назначения создаётся автоматически; существующие данные не перезаписываются.
5. Дождитесь импорта и проверки. В журнале показываются этапы и расположение результата. Путь можно скопировать из поля окна.

При отсутствии готовой среды установщик подготавливает отдельные Python/PostgreSQL и WinSW с проверками существующего установщика; нужен интернет и дополнительное место. Если подходящая среда уже установлена, она используется без остановки рабочей службы.

## Что проверяется

- Дамп импортируется только в новую базу. Количество строк каждой таблицы сравнивается с манифестом внутри транзакции импорта.
- Готовые вложения сверяются с восстановленной БД, размерами и SHA-256 файлов.
- Исходные ключи Django и шифрования сохраняются и проверяются. Пароли тестовой PostgreSQL создаются заново, отдельно от рабочих.
- Для базы используется временная LocalService для организации либо NetworkService для портала. Входящих публичных портов нет: PostgreSQL слушает отдельный loopback-порт.
- SMTP, Telegram, коннектор, корневой туннель и обычный рабочий runtime не запускаются.
- Исходные реквизиты остаются в каталоге, который временная служба прочитать не может; это проверяется самим служебным процессом.

После проверки временная служба останавливается и удаляется. Доступ служебной учётной записи к данным и владение файлами отзываются; восстановленная копия доступна администраторам и SYSTEM. Во время запуска PostgreSQL на родительских каталогах временно разрешено чтение атрибутов/проход без наследования прав на исходные настройки.

## Результат

Каталог: `C:\ProgramData\OwnDesk\Recovery\<идентификатор>\staged`.

| Элемент | Содержимое |
|---|---|
| `recovery.json` | Подтверждение завершения, остановки базы, проверки ключей и файлов |
| `backup-manifest.json` | Манифест исходной копии |
| `original-config` | Исходные настройки, ключи и реквизиты, доступные только администраторам/SYSTEM |
| `probe/pgdata` | Восстановленный отдельный кластер PostgreSQL |
| `probe/private-attachments` | Восстановленные приватные вложения |
| `probe/secrets.json` | Исходные ключи приложения и новые пароли изолированной БД |
| `probe/probe-profile.json` | Профиль проверки; не является рабочим профилем приложения |

Не копируйте эти каталоги поверх работающей установки. В `probe` намеренно отсутствуют обычный `runtime-profile.json`, реквизиты коннектора и туннеля. Простой запуск рабочего runtime из этого каталога не должен публиковать восстановленную копию.

Копии и результаты содержат данные и секреты и не зашифрованы отдельным паролем. Храните их в закрытом хранилище; копия на том же диске не защищает от его поломки.

## Командная строка

Из нового распакованного дистрибутива, PowerShell от имени администратора, с Python из подписанного bootstrap либо установленной среды:

```powershell
$taskPython = "$env:ProgramFiles\OwnDesk\Server\runtime\venv\Scripts\python.exe"
& $taskPython .\infra\windows_recovery.py verify --backup 'D:\OwnDeskBackup'
& $taskPython .\infra\windows_recovery.py recover --backup 'D:\OwnDeskBackup'
```

По умолчанию мастер проверяет готовность импорта до четырёх минут. Очень большие копии могут потребовать отдельной процедуры. После успешной проверки служебный процесс сам ограничивает ожидание контроллера пятью минутами; у временной службы нет автозапуска и бесконечного перезапуска.

Если контроллер принудительно завершили или компьютер выключили, отсутствие подтверждённого `recovery.json` означает незавершённую проверку. Не считайте такую копию готовой к рабочему переключению. Диагностика находится в `probe/service-logs`, `native-command.log`, `initial-restore.log`. Не удаляйте исходную копию при ошибке. Полное возобновление прерванного восстановления и переключение рабочего сервера остаются отдельными этапами.

## Приёмка

На настоящих Windows-службах проверены восстановление тестовой организации с изображением и восстановление копии портала с 42 таблицами. Проверены ключи, файлы, остановка PostgreSQL, удаление служб и итоговые закрытые ACL. Служебный процесс подтвердил отказ в чтении исходных административных реквизитов. Тестовая организация прошла цепочку окно Tk → проверка копии → CLI → временная служба → результат в окне. Работающие портал и Qwerty не переключались.

Восстановление на чистом Windows, после потери всего исходного диска, повтор после отключения питания и запуск приложения из восстановленных данных ещё требуют отдельной приёмки. Linux, S3 и прежние SQLite-копии этим мастером не поддерживаются.
