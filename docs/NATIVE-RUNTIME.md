# Рабочий запуск одной организации без Docker

В 0.4.18 добавлен режим `OWNDESK_RUNTIME=native`: один ASGI-процесс с обработчиком сохранённых заданий, PostgreSQL и закрытым каталогом вложений. Он предназначен для первой небольшой установки, где ещё не нужен отдельный Redis/Celery. Распределённая конфигурация Compose остаётся доступна.

## Устройство и ограничения

Входящие события и исходящие задания сохраняются в PostgreSQL. Обработчик выполняет их из базы каждую секунду, проверяет SLA, периодически применяет политику хранения файлов. Письма обрабатываются отдельным потоком существующего почтового обработчика. После неопределённого результата отправки сообщения не отправляются вслепую повторно. Настройки сроков и неоднозначной отправки сохраняются из общего механизма задач.

Уведомления используют общий слой Channels в памяти одного ASGI-процесса. Отправка из рабочего потока передаётся в цикл ASGI. Второй сервер для того же каталога блокируется. Нельзя запускать несколько API-процессов или дополнительный Celery/beat для этой установки. Слой уведомлений не является хранилищем: клиенты восстанавливают состояние через API после переподключения.

Вложения хранятся в `PRIVATE_MEDIA_ROOT`. Каталог должен быть абсолютным и находиться вне `frontend`, не обслуживаться Caddy и резервироваться отдельно от базы. Доступ к вложениям проходит через API с проверкой организации и прав. Локальный файловый каталог не раздаётся через публичные URL.

Число поддерживаемых одновременно сотрудников и ограничения нагрузки ещё не измерены. Для масштабирования используется отдельная конфигурация с Redis, Celery и S3. Этот выпуск не является готовым универсальным установщиком Windows: подготовка PostgreSQL, окружения и процессов пока выполняется при развёртывании.

## Конфигурация

Нужны Python 3.12, зависимости из `backend/requirements.txt`, PostgreSQL, Caddy и `cloudflared`. Базовые параметры рабочего режима:

```text
DEBUG=0
DEPLOYMENT_MODE=organization
OWNDESK_RUNTIME=native
PRIVATE_MEDIA_ROOT=АБСОЛЮТНЫЙ_ЗАКРЫТЫЙ_КАТАЛОГ
DATABASE_URL=ЗАКРЫТАЯ_СТРОКА_ПОДКЛЮЧЕНИЯ_POSTGRESQL
PUBLIC_BASE_URL=https://АДРЕС_ОРГАНИЗАЦИИ
ALLOWED_HOSTS=АДРЕС_ОРГАНИЗАЦИИ
CSRF_TRUSTED_ORIGINS=https://АДРЕС_ОРГАНИЗАЦИИ
PORTAL_CONNECTOR_STATE_FILE=АБСОЛЮТНЫЙ_ФАЙЛ_ПРИВЯЗКИ
```

Обязательны постоянные `SECRET_KEY`, `TOKEN_ENCRYPTION_KEY` и `ACCOUNT_ENCRYPTION_KEY`. При переносе существующей базы ключи шифрования сохраняются. Не меняйте их при каждом старте. Для писем отдельно настраивается SMTP; отсутствие SMTP не превращает ручное приглашение в отправленное письмо.

После миграций и проверки `python manage.py check --deploy --fail-level WARNING` запустите из `backend`:

```text
python manage.py run_native --port 8000
```

API слушает только `127.0.0.1`. Интерфейс и прокси для туннеля обслуживает [Caddyfile.connector](../infra/Caddyfile.connector). Перед запуском Caddy задайте `OWNDESK_DIST_DIR`, указывающий на абсолютный путь `frontend/dist`. Этот прокси слушает loopback-порт 5173. Для ограничения попыток входа по реальному IP клиента настройте `TRUST_LOOPBACK_CLIENT_IP=1`; прокси передаёт заголовок Cloudflare только во внутренний API.

Запуск коннектора и активация адреса описаны в [INSTALLATION-TUNNELS.md](INSTALLATION-TUNNELS.md). Если сеть не пропускает QUIC, для процесса коннектора можно задать `TUNNEL_TRANSPORT_PROTOCOL=http2`.

## Проверки выпуска

На отдельной базе проверены обработка сохранённых событий, отсутствие повторного исходящего сообщения, защищённые локальные файлы при DEBUG=0 и уведомление из рабочего потока. На реальном HTTPS-адресе проверены владелец, отчёты, изоляция сотрудника, приглашение с публичным адресом, тестовый клиент и длинный ответ, загрузка JPEG и MP4, просмотр и увеличение фото, воспроизведение и увеличение видео в мобильном браузере. Тестовые данные после проверки удалены. Прямой вход с физически другого компьютера и реальная переписка с Telegram-ботом требуют отдельной приёмки.
