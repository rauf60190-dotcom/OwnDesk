ZIP проверен после распаковки в отдельном каталоге. Скрипт Windows установил зависимости в чистое окружение, применил миграции и создал демонстрационное пространство. Проверка `/api/v1/health/ready` вернула HTTP 200. Оба браузерных теста прошли на этом экземпляре, основной путь проверен под ролью оператора. Финальная приёмка по разделу 27 ТЗ требует реального тестового Telegram-бота и инфраструктуры с внешним HTTPS и закрытым S3-бакетом.

## Нагрузка

В отдельном PostgreSQL-пространстве созданы 10 000 свободных обращений одной команды и 100 000 входящих сообщений. 20 сотрудников одновременно выполняли по 6 запросов списка и карточки. Измерялось время обработки в Django через тестовый клиент с настоящей PostgreSQL. HTTP-прокси, сеть, Celery, браузер и внешний Telegram в этот замер не входят.

| Показатель p95 | Результат |
|---|---:|
| Список свободных обращений, подготовленные сессии | 547 мс |
| Карточка, подготовленные сессии | 422 мс |
| Сохранение webhook, 5 событий/с | 73 мс |
| Сохранение webhook, 20 событий/с | 110 мс |

Первый тест выявил 1,39 с для списка. Добавлен индекс порядка очереди, пагинация отделена от загрузки свойств, а таблица выбирает только требуемые поля. Сценарий без предварительного запроса готовности, включающий одновременное создание сессий, показал 1,05 с для списка и 0,44 с для карточки. Холодный результат превышает ориентир в одну секунду. Отдельный тест проверяет, что число SQL-запросов не растёт с числом строк на странице. Полные результаты и описание стенда сохранены в [benchmark.json](benchmark.json) и [benchmark-cold.json](benchmark-cold.json).

## Приёмка на целевом стенде

1. Запустить Compose с настоящим доменом, Redis, рабочими Celery-процессами и приватным бакетом. На машине разработки Docker Engine отсутствовал. Конфигурация прошла `docker compose config --quiet` в Compose v5.7.0. Теги всех пяти образов проверены в реестре. Запуск Linux-контейнеров остаётся проверкой стенда.
2. Пройти путь с настоящим тестовым ботом. Получить сообщение в «Свободных», взять его оператором, ответить в Telegram, решить, закрыть и сверить историю. Повторить в теме группы и проверить Privacy Mode.
3. Проверить фото, документ, видео и голосовое сообщение через реальные Telegram и S3, включая ошибку загрузки, превышение лимита и запрет скачивания посторонним сотрудником.
4. Перезапустить настоящий Redis и worker при входящих событиях и в момент отправки. Проверить восстановление очереди, состояние `unknown` и отсутствие лишней отправки.
5. Выполнить резервное копирование и восстановление Compose + S3 в изолированной среде. Измерить задержку от принятия webhook до отображения сообщения в открытом браузере, затем повторить нагрузку на целевом сервере.

## Границы текущего интерфейса

Настройки сотрудников, команд, компаний, шаблонов и SLA частично доступны также через API. Замена токена, отключение и включение бота доступны в настройках Telegram с подтверждением действия. Расписание SLA редактируется через рабочие дни, интервалы, режим 24/7 и исключения по датам. Поддерживаются перерывы, праздники, сокращённые дни и окончание смены в полночь. Пересчёт действующих сроков выполняется отдельно после сохранения и подтверждения. История действий открывается отдельной панелью карточки. Параллельные изменения справочников пока не имеют общей защиты версий, аналогичной карточке обращения.

## Локальные исправления, 9 ноября 2026

SQLite использует BEGIN IMMEDIATE и ожидание записи до 20 секунд, чтобы избежать конфликта перехода от чтения к записи при одновременной работе входа и фонового обработчика. Регрессионный тест запускает два подключения к отдельной файловой базе и проверяет сохранение обеих записей. Общий запуск серверных тестов: 38 прошли, 2 проверки PostgreSQL пропущены. Режим PostgreSQL этим исправлением не изменён. В браузере прошли три одновременных входа в локальное приложение. Замена токена, отключение, включение и отмена проверены с перехваченными тестовыми ответами API, включая ширину экрана 390 px; реальное подключение не изменялось.

Добавлены просмотр фото и видео с увеличением и ввод до 20 000 символов. Длинные ответы разделяются с сохранением подтверждённых частей, неоднозначная отправка не повторяется автоматически. Проверки длинного текста используют тестовый транспорт и не отправляют сообщения клиентам.

## Воспроизведение

Серверные тесты запускаются из `backend` с `DEBUG=1`, `LOCAL_CHANNELS=1` и `DATABASE_URL` выделенной PostgreSQL. Пользователь базы для испытаний должен иметь право создавать тестовую базу. Тесты создают отдельную БД `test_…`. SQLite подходит для быстрого запуска, но пропускает проверки блокировок PostgreSQL.

```sh
python -m pytest -q
python manage.py makemigrations --check --dry-run
python manage.py spectacular --file ../docs/openapi.yaml --validate --fail-on-warn
```

Для браузерных тестов сначала запустите демоверсию на `127.0.0.1:5173` с `seed_demo`. Из каталога `frontend` выполните `pnpm install --frozen-lockfile`, `pnpm exec playwright install chromium` и `pnpm test:e2e`. Используйте отдельную тестовую базу, поскольку сценарий создаёт и закрывает обращение. Для другого пароля демо-сотрудников задайте `E2E_PASSWORD`.

Для нагрузочного прогона создайте новую пустую БД PostgreSQL с именем `desk_bench_…`, задайте её URL и выполните `python tests/performance/benchmark.py`. Скрипт проверяет имя и пустоту базы перед генерацией данных.
