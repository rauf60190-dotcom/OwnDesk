# Эксплуатация и восстановление

Для текущих служб Windows с управляемой PostgreSQL доступны [согласованные копии без остановки сервера](NATIVE-BACKUPS.md). Команды `Local-Data.ps1` ниже относятся к прежнему локальному режиму SQLite.

## Проверки после запуска

Откройте `/api/v1/health/live` и `/api/v1/health/ready`. Войдите администратором, откройте «Настройки → Состояние системы» и дождитесь актуального heartbeat worker. Проверьте чтение и запись тестового файла через интерфейс пользователя с доступом к обращению.

```sh
docker compose ps
docker compose logs --tail=100 backend worker beat
docker compose exec backend python manage.py check --deploy
```

## Локальная установка Windows

Для чистой установки распакуйте архив, установите Python 3.12 и запустите `Start-OwnDesk.ps1`. Откройте http://127.0.0.1:5173 и завершите настройку владельца с кодом из `.runtime/installation-code.txt`. Для восстановления существующей организации используйте следующую процедуру вместо первоначальной настройки.

1. Остановите нужный локальный сервер (Ctrl+C). В PowerShell из каталога установки запустите команду с путём к новому каталогу копии. Его родительский каталог должен существовать.
2. Храните копию в каталоге с ограниченным доступом. Она содержит чаты, вложения и ключи, с помощью которых сервер расшифровывает данные Telegram и 2FA. Для портала снимок создаётся отдельной командой с `-Profile portal`.
3. Для переноса или восстановления распакуйте ту же версию приложения в новый каталог. До первого запуска из этого каталога выполните команду восстановления. Она сверит контрольные суммы и создаст `.runtime`. Для организации и портала используйте отдельные каталоги назначения.
4. Запустите `Start-OwnDesk.ps1` или `Start-Portal.ps1` в зависимости от восстановленного профиля. Войдите заново. Перед запуском восстановленной организации остановите старый сервер, чтобы два процесса не обслуживали один Telegram-бот.

```powershell
.\Local-Data.ps1 backup 'D:\DeskBackups\organization-01'
.\Local-Data.ps1 backup 'D:\DeskBackups\portal-01' -Profile portal

# Из свежего каталога установки
.\Local-Data.ps1 restore 'D:\DeskBackups\organization-01'
```

При восстановлении старые сессии удаляются. Файлы конфигурации вне `.runtime` и переменные окружения (SMTP, Google OAuth, внешний SECRET_KEY) задаются на новом компьютере отдельно, если использовались. Копия рассчитана на локальную SQLite и файловые вложения из стандартных скриптов запуска. Сценарий для PostgreSQL и S3 приведён ниже.

На отдельных локальных базах проверены оба профиля, вход после восстановления, скачивание вложения, расшифровка секрета 2FA, блокировка копирования при запущенном сервере и отказ при повреждённом файле.

## Обновление и откат на Windows

Распакуйте новую версию в отдельный каталог и остановите прежний сервер. Если с архивом вы получили файл `OwnDesk.zip.sha256`, сравните указанную в нём сумму с выводом `Get-FileHash .\OwnDesk.zip -Algorithm SHA256`. Запустите следующую команду из нового каталога до первого запуска сервера.

```powershell
.\Local-Data.ps1 upgrade 'D:\DeskBackups\before-update-01' -FromInstallation 'D:\ServiceDesk-old'
```

Для портала добавьте `-Profile portal` и используйте отдельный свежий каталог. Укажите прежние параметры окружения, если подключали SMTP, Google OAuth или собственный секрет Django.

Команда создаёт резервную копию, устанавливает зависимости новой версии во временное окружение и применяет миграции к копии базы. При несовместимой схеме или ошибке проверки новая `.runtime` не создаётся. После успешной подготовки запустите нужный скрипт новой версии, войдите, откройте обращение и скачайте вложение. Оставьте прежний сервер остановленным до завершения проверки.

Для отката остановите новую установку и запустите прежнюю из её каталога. Она откроет базу, сохранённую на момент обновления. Записи, принятые новой версией после переключения, останутся в её базе. Если она уже обслуживала Telegram или принимала изменения, сохраните её копию перед переключением и проверьте очередь исходящих действий.

## Резервная копия Linux / Docker Compose

Скрипт для Linux запускается из корня проекта. Укажите новый абсолютный каталог на томе, где достаточно места для базы и всех файлов. Подготовьте короткое окно обслуживания. Скрипт останавливает запись новых данных, выполняет `pg_dump -Fc`, копирует закрытые файлы и проверяет перечень объектов. После завершения он поднимает сервисы. Пока внешний вход остановлен, Telegram может повторить доставку webhook.

```sh
sh infra/backup.sh /srv/backups/desk-2026-11-05
```

Комплект содержит `database.dump`, `SHA256SUMS`, каталог `files` с манифестом и телами объектов. Для каждого файла проверяются UUID, пространство, ключ, длина и SHA-256. Храните комплект в защищённом месте. База содержит историю клиентов и зашифрованные токены. Ключи TOKEN_ENCRYPTION_KEY и ACCOUNT_ENCRYPTION_KEY, секрет Django и доступ к S3 сохраните отдельно.

## Восстановление Linux / Docker Compose

1. Подготовьте отдельный каталог проекта, отдельное имя Compose-проекта и пустую базу. Подготовьте закрытый бакет назначения. Укажите параметры этого бакета и исходные `TOKEN_ENCRYPTION_KEY`, `ACCOUNT_ENCRYPTION_KEY` и `SECRET_KEY` в `.env`.
2. Проверьте путь к копии и запустите скрипт ниже. Он проверит контрольные суммы, наличие пустой базы и выполнит восстановление базы в одной транзакции. Файлы будут записаны только после проверки всего манифеста.
3. Проверьте миграции, войдите сотрудником, откройте ранее сохранённое обращение, сравните историю и скачайте файл. Отдельно проверьте отказ для сотрудника из другого пространства.
4. До включения работников проверьте исходящую очередь. Используйте изолированный тестовый бот или отключите внешнюю маршрутизацию на стенде восстановления. Переключайте рабочий webhook только после проверки стенда.

```sh
export COMPOSE_PROJECT_NAME=service-desk-restore
sh infra/restore.sh /srv/backups/desk-2026-11-05
docker compose run --rm --no-deps backend python manage.py migrate --noinput
```

На отдельном стенде PostgreSQL 17.11 и SeaweedFS 4.53 проверены выгрузка и восстановление непустой базы в другую базу, а также перенос двух вложений в отдельный закрытый бакет через S3 API. Сверены контрольные суммы обращений, сообщений и вложений. Проверены вход после восстановления, скачивание файлов, запрет анонимного доступа и отказ при подмене файла до записи объектов. На PostgreSQL прошли 78 тестов. Один тест предназначен для SQLite.

Проверены синтаксис обоих скриптов и конфигурация Compose. Команды экспорта и восстановления вложений запускаются с UID и GID пользователя, который читает закрытый каталог копии на хосте. Полный запуск Linux-стека под Docker и проверка HTTPS на целевом сервере остаются отдельными шагами приёмки.
