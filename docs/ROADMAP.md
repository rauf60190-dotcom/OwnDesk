## Этап 1 — владелец и приглашения: реализован

Владелец обозначается отдельным признаком Membership.is_owner и сохраняет административную роль. Это позволяет сохранить существующие проверки доступа операторов и руководителей. Новые организации получают владельца при создании. Миграция существующих организаций выбирает первого действующего администратора по дате создания; остальные учётные записи сохраняются. Организации без действующего администратора требуют отдельного восстановления доступа.

Настройки → Сотрудники: владелец или администратор вводит email, выбирает роль и команду и создаёт приглашение. Ссылка выдаётся один раз, действует 72 часа и передаётся вручную. При настроенном SMTP можно выбрать отправку приглашения по почте; ссылка также доступна для ручной передачи. Повторное приглашение на тот же адрес отменяет прежние непринятые ссылки.

Приглашённый сотрудник задаёт свой пароль, а существующий пользователь подтверждает вход в свой аккаунт. Пароль существующего аккаунта приглашением не заменяется. Акцепт создаёт членство в указанной организации и команде, без новой организации. Вручную переданная ссылка не подтверждает владение email. Администраторов приглашает и изменяет только владелец. Владельца нельзя отключить или понизить через обычное редактирование сотрудников. Передача владения доступна отдельной формой с повторным подтверждением пароля и 2FA.

Непустые email уникальны без учёта регистра. При обновлении установки с дубликатами миграция должна быть остановлена до разрешения конфликта: автоматически удалять или объединять аккаунты нельзя. В текущей рабочей базе дубликаты не обнаружены.

Проверки: 64 серверных теста прошли, 2 требуют PostgreSQL. Браузер на отдельной тестовой базе проверил приглашение, принятие, доступ оператора в организацию владельца, отключение сотрудника и ширину 390 px. Рабочие чаты и сотрудники не использовались для теста.

## Этап 8 — доступ к установке компании через поддомен OwnDesk

Компания устанавливает сервер у себя и получает отдельный адрес на домене OwnDesk. Коннектор устанавливает исходящее соединение с Cloudflare. Сотрудники открывают HTTPS-адрес своей организации, а приглашения формируются с этим адресом.

В 0.4.13 подготовлена привязка установки к аккаунту портала. В разделе «Мои установки» владелец выдаёт одноразовый код на 15 минут. Команда `connect_portal` сохраняет отдельный ключ установки, выполняет привязку и отправляет сигнал связи каждые 30 секунд. Повторная попытка с тем же ключом восстанавливает привязку после сетевой ошибки. Владелец может отозвать привязку, после чего коннектор теряет доступ к API подключения.

Следующий слой — автоматическое создание отдельного туннеля и DNS-записи для установки через ограниченные серверные реквизиты Cloudflare. После этого коннектор получает конфигурацию, запускает туннель, задаёт публичный адрес организации и проходит проверку HTTPS. Отзыв публичного доступа должен отключать маршрут Cloudflare. Состояние привязки и состояние доступности рабочего сервера показываются отдельно.

В 0.4.16 реализована серверная подготовка ресурсов командой `prepare_public_route`: выделенный туннель, постоянный адрес установки, восстановление после потерянного ответа, защита существующей DNS-записи и отключение маршрута перед отзывом привязки. В кабинете видны состояние подготовки и hostname. Подготовленный маршрут закрыт и отвечает 404. Выдача токена коннектору, его автоматический запуск, защищённая конфигурация приложения и проверка HTTPS ещё не реализованы. Порядок настройки: [INSTALLATION-TUNNELS.md](INSTALLATION-TUNNELS.md).

В 0.4.17 добавлены API конфигурации и активации, подписанная проверка публичного origin и команда `run_connector`. До подтверждения готовности доступен только endpoint проверки. Коннектор требует рабочее окружение с DEBUG=0, точным hostname, HTTPS-origin, secure-cookie, постоянным секретом и PostgreSQL. Он управляет одним дочерним `cloudflared`, повторяет проверки, перезапускает его после завершения и останавливает при отзыве. В кабинете ссылка активна только после свежей успешной проверки. Следующие работы: настроить реальные серверные реквизиты Cloudflare, развернуть совместимую версию портала и рабочего сервера, проверить подключение и приглашение с другого компьютера. Подготовка рабочего окружения и служба Windows остаются этапом установщика.

Для первой публичной установки требуется рабочая конфигурация сервера организации с выключенным DEBUG и стойким паролем владельца. Приёмка включает приглашение с другого компьютера через отдельную сеть, загрузку вложений, перезапуск коннектора и отзыв доступа.

## Этап 9 — мастер установки Windows

В 0.4.19 начат общий сценарий самостоятельной установки: запрос конфигурации коннектором автоматически создаёт выделенный туннель и DNS, ручная команда администратора портала больше не нужна. В мастере добавлена подготовка адреса, отображение hostname и отдельная проверка фактического публичного доступа. Следующие блоки: проверяемая подготовка зависимостей Windows, общий рабочий запуск из дистрибутива, безопасный перенос данных и служба. Подробный порядок: [SELF-INSTALLATION.md](SELF-INSTALLATION.md).

В 0.4.18 подготовлен нативный рабочий запуск без Docker для одной организации: PostgreSQL, один ASGI-процесс с обработчиком заданий, закрытый каталог вложений, Caddy и коннектор. В первой установке копия данных мастера перенесена с сохранением аккаунта владельца и исходной базы. Проверены публичный HTTPS и функциональные сценарии в независимых браузерных сессиях. Следующие шаги — проверка с физически другого компьютера, настоящий Telegram-бот и SMTP, автоматический установщик и служба Windows. Общий мастер миграции данных для всех пользователей ещё не встроен.

В 0.4.14 добавлен мастер в стиле OwnDesk с этапами приветствия, создания организации, настройки владельца, привязки к порталу и проверки готовности. `Setup-OwnDesk.cmd` подготавливает приложение и открывает мастер в браузере. Одноразовый код запуска передаётся во фрагменте URL и удаляется из адреса при открытии. Из формы владельца можно привязать установку по коду портала. При запуске через Windows-скрипт фоновая проверка связи выполняется вместе с сервером.

Следующие части установщика — сборка EXE с проверкой зависимостей, запуск сервера как службы Windows, автоматический старт при включении компьютера, состояние и диагностика службы в интерфейсе, а также подключение выделенного публичного туннеля. На этом этапе браузерный мастер использует текущий пользовательский запуск сервера.

## После публичной приёмки — требования к оборудованию

Добавить на страницу регистрации и в раздел «Установка» ссылку «Требования к серверу». Указать отдельно минимум для знакомства, рекомендуемую конфигурацию для небольшого рабочего сервера и требования к ноутбуку сотрудника. Для каждого сценария описать число ядер CPU, объём RAM и свободного места, ОС и зависимости. Для сервера указать, как учитывать PostgreSQL, резервные копии и объём фото и видео. Числа определить по замерам на чистой установке и обозначить нагрузку, при которой они проверены.
