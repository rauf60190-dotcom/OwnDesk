# Резервные копии служб OwnDesk на Windows

Для Linux Compose используются отдельные [команды и расписание](LINUX-BACKUPS.md).

Команда `infra/native_backup.py` создаёт копию работающей установки с управляемой PostgreSQL: логический дамп, готовые приватные вложения, исходные ключи и закрытую конфигурацию. Служба не останавливается, её пароль и данные не изменяются. Linux-профиль с отдельным контейнером PostgreSQL этой командой пока не поддерживается.

## Создать и проверить копию

Распакуйте дистрибутив с инструментом копирования. Из его каталога откройте PowerShell от имени администратора Windows. Выберите новое имя каталога для каждой копии:

```powershell
$taskPython = "$env:ProgramFiles\OwnDesk\Server\runtime\venv\Scripts\python.exe"
& $taskPython .\infra\native_backup.py backup `
  --data "$env:ProgramData\OwnDesk\Server" `
  --output "$env:ProgramData\OwnDesk\Backups\organization-before-update-01"

& $taskPython .\infra\native_backup.py verify `
  --output "$env:ProgramData\OwnDesk\Backups\organization-before-update-01"
```

Для портала замените `Server` на `Portal`, а имя копии — например, на `portal-before-update-01`. Используйте Python установленной службы с её зависимостями. Команда записывает версию установленного приложения, которая может отличаться от версии архива с инструментом копирования.

Копии создаются только в новых непосредственных подкаталогах `C:\ProgramData\OwnDesk\Backups`. Каталог закрывается точным ACL: полный доступ только у администраторов Windows и SYSTEM. Ни LocalService, ни NetworkService не получают доступа. Существующий каталог не перезаписывается. Копии содержат секреты и не зашифрованы отдельным паролем; переносить их следует только в закрытое хранилище. Копия на том же ноутбуке не защищает от поломки его диска.

## Согласованность

Одна транзакция PostgreSQL фиксирует снимок данных и удерживает разделяемые блокировки готовых вложений. Дамп использует тот же [экспортированный снимок PostgreSQL](https://www.postgresql.org/docs/17/app-pgdump.html). Очистка по сроку хранения, которая блокирует эти же записи перед удалением файлов, ждёт завершения копирования. Новые сообщения и вложения после момента снимка не входят в эту копию.

Пароль PostgreSQL передаётся процессу через окружение, не через аргументы командной строки. Ключи и конфигурация проверяются повторно в конце; при их изменении копия не завершается. Проверяются размер и SHA-256 каждого сохранённого файла. Манифест `manifest.json` публикуется последним, только после успешного копирования. Каталог без него не является завершённой копией; при ошибке исходные данные остаются на месте. Журнал `database.log` также хранится внутри закрытого каталога.

Старый журнал одноразового импорта `_owndesk_restore_receipt` исключается из дампа: он относится к прежнему переносу и не должен мешать восстановлению новой копии. Нельзя одновременно запускать миграции схемы и создание копии. Блокировка, которую не удалось получить за пять секунд, завершает попытку ошибкой; после устранения причины повторите команду с новым каталогом.

## Восстановление

В установщике добавлен [мастер восстановления в отдельный закрытый стенд](NATIVE-RECOVERY.md). Он проверяет базу, вложения и ключи, затем останавливает тестовую базу без публикации. Переключение рабочего сервера пока выполняется отдельной процедурой. Перед ним требуется:

1. Проверить копию командой `verify`. Подготовить совместимую версию приложения и пустую базу с отдельной ролью приложения. Рабочую базу не перезаписывать.
2. Восстановить `database.dump` через `pg_restore --single-transaction --no-owner --no-privileges`. Сверить количество строк с `counts` манифеста.
3. В отдельный закрытый каталог восстановить перечисленные приватные файлы и конфигурацию. Сверить контрольные суммы. Сохранить исходные Django/Fernet-ключи: без них зашифрованные реквизиты и 2FA не расшифруются.
4. Перенастроить абсолютные пути и порты в профиле под стенд. Если дамп уже восстановлен вручную, убрать прежнее поле `initial_restore`: оно указывает на архив исторической миграции, а не на новую копию. Для свежей автоматической загрузки нужен отдельный профиль с новой контрольной суммой и счётчиками.
5. Проверять базу и файлы без коннектора, корневого туннеля, SMTP и Telegram. Не запускать вторую копию рабочей организации с теми же внешними реквизитами. Рабочий маршрут включается после проверки и остановки исходного экземпляра.

Не запускайте старые каталоги `work/laptop-portal` и `work/connected-installation` для отката: после переключения в службы на рабочем сервере могли появиться новые записи. Перенос новых данных и обратное переключение требуют отдельной процедуры.

## Что проверено

На изолированной PostgreSQL 17 проверены общий снимок при конкурентной записи, ожидание блокировки очисткой файлов, восстановление дампа в отдельную пустую базу, восстановление приватного изображения и ключа расшифровки. Новая запись осталась в исходной базе и отсутствовала в раннем снимке. Проверены отказ при повреждённом файле, незавершённом манифесте, выходе пути за пределы копии и существующем каталоге назначения.

Этот сценарий не заменяет полную аварийную приёмку на другом компьютере и восстановление внешних интеграций.
